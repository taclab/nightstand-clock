# Audit de Nightstand Clock avant soumission communautaire

Date : 22 octobre 2026. Code examiné : commit `26ca52d`, manifeste `1.0.1`.
Release publique examinée : `v1.0.1`, construite au commit `4f2e175`.
Le code du plugin, les assets, le SDK, les outils et le workflow sont identiques entre ces deux commits ; le changement suivant concerne le README.

**Verdict : le paquet passe le contrôle automatique de soumission, mais des corrections de stabilité et de comportement sont recommandées avant de le proposer à la communauté.**

Aucune soumission, issue, modification de release ni publication n'a été effectuée. Cet audit ajoute uniquement ce document au dépôt ; le code reste inchangé.

## Constats prioritaires

### 1. P1 — Des événements rapprochés peuvent désactiver le plugin

Emplacement : `src/nightstand/clock/NightstandClockPlugin.java:130`, appel à `publishScreensaverAsset` ligne 135 ; déclenchement depuis `onEvent` lignes 78–88.

Chaque modification des options provoque immédiatement une publication. La comparaison avec `published` supprime les doublons, mais ne limite pas la fréquence des changements réels. Un capteur de luminosité oscillant autour du seuil, par exemple `9, 11, 9, 11, 9` avec un seuil de 10, produit cinq publications si ces événements sont livrés dans la même fenêtre d'une seconde. Les mises à jour météo et les modifications de paramètres partagent ce même budget.

Kiosk Satellite autorise quatre changements d'économiseur par seconde. Le cinquième lève une exception ; une exception non interceptée dans un callback fait arrêter et désactiver le plugin. La documentation indique également que les événements d'entité sont regroupés sur 100 ms : leur fréquence maximale peut donc dépasser celle autorisée pour les publications.

Correction : regrouper les changements, limiter les publications selon le budget du host et garantir une publication différée du dernier état. Une hystérésis du mode nuit peut réduire les oscillations, mais ne remplace pas cette limite globale. Respecter le thread de callbacks et annuler le travail différé à l'arrêt.

Validation attendue : faire évoluer un faux host avec la limite réelle, livrer cinq changements dans une seconde, vérifier l'absence d'exception puis la publication du dernier état. Le faux host actuel compte les publications sans appliquer de limite.

Preuve : chemin de code local confronté au [budget du host](https://github.com/jxlarrea/kiosk-satellite/blob/main/app/android/app/src/main/kotlin/me/jxl/kiosk_satellite/plugins/PluginScreensavers.kt), à sa [gestion des erreurs](https://github.com/jxlarrea/kiosk-satellite/blob/main/app/android/app/src/main/kotlin/me/jxl/kiosk_satellite/plugins/PluginBridge.kt) et au [contrat des abonnements](https://github.com/jxlarrea/kiosk-satellite-plugins/blob/main/docs/home-assistant.md). Non reproduit sur appareil pendant cet audit.

### 2. P2 — Changer le seuil de nuit ne recalcule pas l'état

Emplacement : `src/nightstand/clock/NightstandClockPlugin.java:43`, notamment lignes 55–59 et 85–86.

Scénario : le capteur vaut 15, le seuil vaut 10, le mode nuit est donc désactivé. Passer le seuil à 20 devrait activer immédiatement le mode nuit. `configure()` conserve pourtant `nightActive` lorsque l'identifiant d'entité ne change pas. Le recalcul n'arrive qu'au prochain événement du capteur, ce qui peut prendre longtemps si sa valeur est stable.

Correction : conserver le dernier snapshot du capteur et recalculer l'état lors de chaque configuration pertinente, ou demander explicitement un nouveau snapshot. Effacer ce snapshot en cas de changement d'entité.

Validation attendue : snapshot à 15, seuil initial 10, puis `configure` avec 20 sans nouvel événement ; `nightActive` doit passer à `true`. Vérifier aussi le changement inverse. Constat établi par lecture du code, sans exécution Java locale.

### 3. P2 — Un fond clair reste lumineux en mode nuit

Emplacement : `assets/standby/standby.css:13`, `:root.night`, et lignes 19–24 / 44.

Le mode nuit change les couleurs du dessin et réduit l'opacité de `#root`, mais le fond de `html` et `body` conserve la couleur configurée pour la journée. Avec un fond blanc, le mode nuit laisse donc tout l'écran blanc, même à 20 % de luminosité. Le dessin rouge devient rose pâle sur ce fond. Cela contredit la fonction annoncée de garder la pièce sombre.

Reproduction navigateur : options `{"night":"always","background":"#FFFFFF","nightBrightness":20}`. Après la transition, le fond calculé reste `rgb(255, 255, 255)` et l'opacité de `#root` vaut `0.2`. Capture examinée visuellement.

Correction : utiliser un fond noir en mode nuit, ou ajouter une couleur de fond nocturne distincte et sombre. Le réglage global de luminosité du host reste indépendant.

### 4. P2 — Les extrema météo ne sont pas rattachés au jour affiché

Emplacement : `src/nightstand/clock/Weather.java:50` et `src/nightstand/clock/NightstandClockPlugin.java:92`.

`today()` prend toujours le premier élément de la liste sans lire son `datetime`. Une liste commençant demain produit donc les extrema de demain, alors que le README annonce ceux d'aujourd'hui. Le cache ne conserve ensuite que deux nombres, sans date ni expiration effective à l'affichage.

Le délai de 30 minutes limite seulement les appels déclenchés par un événement météo. Il ne programme aucun rafraîchissement. Sans nouvel événement, les valeurs peuvent rester affichées après minuit ; en cas d'échec d'une nouvelle requête, les anciennes valeurs restent également utilisables sans limite de fraîcheur.

Correction : sélectionner une entrée correspondant à la date voulue selon une règle de fuseau explicite, conserver sa date et masquer les extrema devenus périmés. Prévoir un rafraîchissement indépendant des changements de température si l'objectif est une actualisation périodique.

Validation attendue : liste commençant demain, passage à minuit, liste vide, réponse tardive, erreur réseau et reprise. Les prévisions Home Assistant contiennent un [champ `datetime`](https://www.home-assistant.io/integrations/weather/). Constat de code ; comportement d'un fournisseur réel non testé ici.

### 5. P2 — La date de l'horloge analogique plein écran est reformattée à chaque image

Emplacement : `assets/standby/standby.js:41`, `:253` et boucle `requestAnimationFrame` à partir de la ligne 410.

Avec les secondes activées, l'horloge plein écran reconstruit un `Intl.DateTimeFormat` à chaque image pour une date qui ne change qu'une fois par jour. La comparaison `today !== day` évite une écriture DOM, mais intervient après le travail de formatage.

Instrumentation dans Chrome : **61 constructions de formateur en une seconde**, une fois le document et les polices chargés. Cela représente du travail évitable en continu sur les appareils modestes visés. L'effet sur le CPU, la température ou la fluidité d'un Echo Show n'a pas été mesuré.

Correction : conserver les formateurs et ne reformater la date qu'au changement de jour ; continuer à déplacer les aiguilles à chaque image. Dans l'horloge numérique plein écran, comparer aussi des chaînes normalisées de la même manière : le texte capitalisé mémorisé dans `day` diffère du texte source français, ce qui provoque des écritures inutiles chaque seconde.

## Sécurité et confidentialité

- Aucun mécanisme d'exfiltration, secret embarqué, commande shell ni chargement de code distant identifié dans le code applicatif examiné.
- Les contenus météo et noms de lieux sont insérés via `textContent`, pas par concaténation de HTML. Les couleurs sont filtrées et les nombres non finis rejetés côté Java.
- Les permissions correspondent aux fonctions : `screensaver` pour le rendu, `host.read` pour les états et `ha` pour `weather.get_forecasts`. La requête HA utilise un domaine et un service fixes.
- Le JavaScript du plugin ne réalise aucun appel réseau. Le blocage réseau du WebView repose sur le [contrat de rendu de Kiosk Satellite](https://github.com/jxlarrea/kiosk-satellite-plugins/blob/main/docs/screensavers.md), pas sur un sandbox propre au plugin Java.
- Les souscriptions inutilisées sont retirées. Les réponses météo tardives sont protégées par une révision et un indicateur de vie de session.
- Les licences Apache-2.0 et SIL OFL de la police sont présentes ; le README attribue le SDK et les outils à leur origine. Il ne s'agit pas d'une expertise juridique sur l'origine de chaque asset.

Aucune vulnérabilité critique identifiée dans ce périmètre. Cette conclusion ne couvre ni un test d'intrusion du host, ni l'ensemble de l'historique Git, ni une validation sur appareil réel.

## Améliorations de maintenance avant diffusion

1. Ajouter une CI de validation sur `pull_request` et `push`. Le seul workflow actuel se déclenche à la publication d'une release ou manuellement sur un tag ; les régressions peuvent donc être découvertes après publication du tag.
2. Compléter les tests métier pour les cinq constats ci-dessus et intégrer quelques tests du renderer. Les 31 tests Python valident surtout l'outillage ; ils ne garantissent pas le comportement de l'horloge.
3. Documenter les versions de Kiosk Satellite et WebView réellement testées, ainsi que le matériel. `minAndroidSdk: 24` ne suffit pas à garantir le support de toutes les fonctions CSS utilisées sur d'anciens WebView.
4. Préciser que le format d'heure automatique suit la locale, comme l'indique le manifeste ; il ne lit pas le réglage Android indépendant 12/24 h. Décider également du comportement attendu quand le capteur de nuit est indisponible : aujourd'hui, cela désactive le mode nuit.
5. Ajouter un court changelog et des indications de reproduction pour les rapports de bugs. Facultatif pour l'admission, utile pour les utilisateurs et mainteneurs.
6. En durcissement de la chaîne de publication, envisager de figer les actions tierces par SHA et de limiter `contents: write` au job qui publie. Ce n'est pas un échec du contrôle officiel.

## Validation finale recommandée après corrections

- Rejouer les tests métier et outils, puis reconstruire le paquet.
- Vérifier sur un appareil cible les changements de seuil, un capteur instable, la déconnexion/reconnexion HA, le passage à minuit et les transitions veille/réveil.
- Vérifier les orientations, le mode Now Playing et les fonds clairs/sombres dans le WebView réel.
- Mesurer la charge de l'horloge analogique plein écran avant/après correction du formatage.
- Lorsque la publication sera explicitement décidée, créer une nouvelle release depuis le commit corrigé puis rejouer le contrôle officiel avant de soumettre.
